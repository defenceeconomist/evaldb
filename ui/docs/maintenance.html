Keep the evidence, its selection decision and the design rationale together.

Editorial workflow

  1. Screen: apply C1–C8 to the primary report and record an include, include-with-limits, hold or exclude decision. Check title, identifier, date, URLs and previous editions for duplication.
  2. Extract: write concise questions, methods, findings and recommendations. Record sample, period, design and limitations to the level needed for the stated use. Use PDF file pages or named HTML sections.
  3. Apply: add a single decision-use sentence, case tags, controlled topics and a specific transfer boundary. Label analyst judgements; do not create missing findings.
  4. Check: read the cited passages; check important numbers and translations. Have a second analyst review decision-critical material where possible. The current screening was not a second independent appraisal.
  5. Publish: rebuild, validate, inspect the interface and update the changelog. Keep source-check, summary and editorial-review dates separate.
  6. Revisit: check links and new editions at least every six months, and assess supersession when a relevant report appears. Reappraise a source whenever a decision-critical use is proposed.

These intervals are recommended editorial practice; no automatic monitoring or background updates are configured. Next scheduled editorial check: by 17 March 2027, subject to an owner adopting this process. The collection owner and second-reviewer role are not yet assigned in the data.

Files and regeneration

The website is in ui/dist/. The live Mac mini portal serves this directory at /evaluation-database/; documentation is at /evaluation-database/docs/. Relative links work beneath this route, at a site root or from local files. Only the public site directory should be served.

  • ui/content/catalogue.json: source catalogue and report summaries, retaining stable EVAL IDs.
  • ui/content/review.json: editorial selection decisions, criterion results, topics, uses, boundaries and corrections.
  • ui/content/*-fields.json: original CSV column order; review fields are appended.
  • ui/docs/*.html: editable handbook content. The build supplies navigation and generates the complete record review.
  • ui/scripts/build_site.py: standard-library builder. Run python3 ui/scripts/build_site.py from the database folder.
  • ui/dist/data.js, CSV files and ui/dist/docs/*.html: generated content. Do not edit these directly.
  • ui/dist/index.html, evaluation.html, app.js, styles.css: authored interface files; no package installation is required to serve them.

The build validates record identity, complete screening, permitted case names, related-record references and CSV row integrity. It also updates the parent outputs/ CSVs when that directory exists. For an existing legacy research rebuild, .research/build_summaries.mjs now invokes the review builder with --import-catalogue after generating the base records. New records need review entries before they can be published. The older Excel selectors and synthesis documents remain historical snapshots.

Field conventions

FieldMeaning
evidence_type / evidence_familyReviewed specific design/type and discovery family. Original source categories remain in the catalogue.
selection_status / criteria_resultsEditorial disposition and separate C1–C8 gate decisions; not a risk-of-bias rating.
decision_use / business_case_usesAnalyst-proposed application and one or more five-case dimensions.
topicsAcquisition & support; Digital & data; Estates & infrastructure; Governance & finance; Innovation & industry; People & culture; Readiness & resilience; Training & skills.
transfer_boundaryScope, design, time or context restrictions relevant to the proposed use.
evidence_access_basis / access_levelWhat was actually consulted and the corresponding discovery filter. Full-report access is not a quality rating.
related_recordsPotential thematic or study overlap; does not assert formal replication or supersession.
DatesReport date and public release date describe the source; summary date describes extraction; source-check date describes earlier link verification; review date describes editorial screening.

How to capture a new design consideration

Add a numbered entry to ui/docs/design-decisions.html with the problem, decision, reason, trade-off, date and any affected criteria or fields. Add an entry below to explain changed behaviour. Rebuild the handbook and verify its links. Keep proposals distinct from implemented behaviour.
